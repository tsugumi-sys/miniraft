## 前提

### Raftって何？なぜ必要なの？
Raft:

そもそもRaftは合意形成の分散アルゴリズム。
合意形成とは、leader/followerの選択に限らず、複数ノード間で同じ内容・同じ順序の状態変更を共有するということ。


e.g.,
3つのノードがある。A,B,C
クライアントから
x = 10
y = 20
x = 30

という処理を受け取ったとする。
全てのノードで

x=10 -> y=20 -> x=30

という順番で処理されたということを共有する。このためにRaftが使われる。
全てのノードが上の状態を同時に共有できている必要はない。commitされたログの順番は常に全てのノードで同じである必要がある。Followerは一時的に遅れていても良い。


普通に共有じゃなぜダメなのか？
例えば、受け取るノードが違う。x=10をA, その後, y=20をB, そしてx=30をCが受け取る。
この時、Aは後の処理をまだ知らない。Aに問い合わせたら、y=20,x=30の変更がなくなっているように見える。

x=10を受け取ったら、その事実をB, Cにも伝えないといけない。システム全体として、x=10の変更を受け取ったとしなければいけない。
y=20をBが受け取ったら、その事実をA,Cに伝えないといけない。

この時、Cにはx=10,y=20の順番で届く可能性もあるし、y=20,x=10の順番で変更が届く可能性もあるわけだ。
どっちが正しい順番だろう？

システム全体で、変更をどの順番で適用するのか、Raftはこの問題を解こうとしている。


### じゃあ全部Leaderに書き込めばいいじゃん

じゃあ中央集権サーバー的なのがいて、それが管理すればいいじゃん。

Leaderが死んだらどうなるか。書き込めなくなる。ノードはあと2つあるのに。

Aが死んだらどうする？

```
A: グエー!!


B: 俺がリーダーになろうか？
C: 俺もリーダーになろうか？
→ BC: どうぞどうぞ
```

みたいにリーダーをどう選ぶかが決まらない。リーダーを選ぶシステムを置く？そのシステムが死んだら？単一障害点になりうる。

他にもネットワーク障害が発生しただけで、実際は誰も死んでないケース

```
A: 生きてるぜ

---------- 障害 ----------

B,C: ワイら生きてるけど、リーダー死んだぽいな。
```

こうなると、リーダーが2つになる可能性がある。(split brain)

### Raftが解きたいこと

中央管理サーバーなし（単一障害点なし）で、変更をどの順番で適用するのかをシステム全体で合意させたい。この問題をRaftは解きたい。

## Leaderをどう選ぶか

Raftが使われる最も有名なケースの一つは、リーダー選択。Leaderが死んだ、死んだように見える、場合に、安全にどうリーダーを選択するか。
正しく選べないとsplit brainのような問題が発生しうる。

この問題で解きたいことを書き直すと、

固定リーダーは単一障害点になってしまう。そこで、Leaderが障害になっても残ったノードから安全にリーダーを選びたい。


### じゃあAが死んだことをBとCはどう判断する？

B/Cからみて、実際にAが本当に死んだのか、ネットワーク障害で死んだように見えるのかは判断ができない。

愚直にやるなら、一定間隔でAに対して、B, Cからメッセージを送り続ける。一定時間内に返信がなかった時、Aを死んだとみなす方法だ。

B,C ----- polling ----> A
B,C <---- reply   ----- A


Raftではこのように一定時間のメッセージ送信で検知している。ただし、B,Cから送るのではなく、AからB,Cに対して送っている。


B,C <---- msg push ---- A

(実際にはRPCを使っており、request/response型ではある)

なぜpollingではないのかというと、無駄を減らすため。基本的にLeaderからFollowerに対してはlog replicationを実施するため、
常にメッセージを送り続けている。したがって、LeaderであるAからメッセージを送り続けることで、それをB/Cは受信できれば、Aが生きていることを
確認できる。replicationするログがない場合でも、空のログを送ることによってheatbeatとして監視するようにしている。

逆にAは, BやCが死んだことを認識するのか？実は、死んだまでは判断できない。ただ、死んだかもと認識する。上のメッセージに対する返答がない場合。
それでも、Bだけが死んだ場合では、Cは生きているとわかるので、まだ過半数のノードが生存しているからクラスタは正常な状態を保ち続けることができる。

### A（Leader）が死んだ場合、いつBとCはElectionを開始する？

同時に開始すると衝突が発生してしまう。
すぐ始めなければいいので、ランダムに始める時間を遅らせてみるのは一つの手だろう。

1. Leaderからのメッセージが一定以上来ない
2. 昇格を開始

実際にRaftではこの方式をとっている。一定以上 = Election Timeoutと呼ばれている。
このElection Timeoutをランダムにする。完全に衝突は防げないが、衝突した場合は再度
やり直せばいい。そうするといつか衝突を避けることができる。


### Electionはどう実行されるの？

1. Election Timeoutが発火

A: Leader dead...
B: Follower election timeout!
C: Followe 


2. Bはfollower -> Candidateになる。

まだLeaderにはならない。候補となる。

3. Bは他のノードに投票をリクエストする

RPCでリクエストを送信。

4. CがBに投票する。

すると、B自身を含めて3台中2台のmajorityが取れる。


衝突が起きる場合は、BとCがどちらもCandidateになったケース。ただこちらは、どちらも過半数の投票を取得できないため、やり直しとなる。


BのLeader Electionが完了した後、Aが復帰したとする。この場合、リーダーが2つになってしまう。もしこれらのリーダーが同時に別々の命令をcommitしてしまった場合、
システム全体のデータ整合性が壊れてしまう。これを防ぐために、commitには過半数ノードの合意が必要（quorum）であるようにする。古いリーダーがなぜ生まれるかというと、
ネットワーク分断によるものだ。したがって、古いリーダーは過半数のフォロワーと通信ができない、したがって合意形成ができないため不正なcommitを防ぐことができる。
そして、リーダー自身がネットワークに再び参加した時、どう自分は古いと認識すればいいか。これにはtermと呼ばれる、選挙の世代を区別する概念を取り入れる。
つまり、今最新のtermと自分の認識するtermを比較することで、自分が遅れているかどうかわかる。遅れている場合は、followerに降格する。


### 何を基準に投票するの？

以下メモ:
「Cは何を基準にBへ投票するの？」

単に

まだ誰にも投票してない
→ Bに投票！

では危ない。

例えば、

B log: [x=10]
C log: [x=10, y=20, x=30]

だったら、古いデータしか持っていないBをLeaderにして本当にいいのか？これではデータが失われてしまう。
Candidateが自分はこの世代の選挙に参加しており、ここまでのログを処理した、という情報を有権者に公表する必要がある。

```
RequestVote{
- term: 3 // 今の選挙のterm
- candidate: B
- latestLogIndex: 52 // 最後に処理されたログの位置
- latestLogTerm: 2 // 最後のログが処理された時のterm
}
```

Candidateは現在のtermに加えて、latestLogTerm,latestLogIndexを公開し、各Followerは自分より古いCandidateを投票対象から除外する。
投票可否は、

- Candidateのログが自分と同等かより新しい
- かつそのtermで他のCandidateに投票してない

で決まる。これにより、commit済みのログを持たない古いCandidateがLeaderになることを防ぐ。commit時にQuorumによって必ず過半数は最新のログを
処理していることが決まっているので、例えばCandidateが2つあって、最新でないログを持っている方のRequestVoteが先にfollowerに届いたとしても、
最新ログを持つfolloweによって投票拒否されるため投票過半数を得ることはできない。
